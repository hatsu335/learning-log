# rework-commits スキル 利用ガイド

Cursor Agent 向けスキル `rework-commits` の概要、メリット、配置方法、使い方をまとめたドキュメントです。

---

## 1. このスキルとは

`rework-commits` は、**1本のブランチを「レビューしやすい小さな意味単位のコミット列」に組み替える** ための手順書（`SKILL.md`）です。

エージェントがこのスキルに従うことで、次のような作業を一貫した手順で実行します。

- 作業前の安全確認（未コミット変更の有無、main への rebase 確認）
- 復旧用のコミットハッシュ記録
- 変更内容のパッチ保存と検証
- 論理的なコミット分割（DB → バックエンド → フロントエンド）
- レビュー向けのコミットメッセージ作成

---

## 2. 利用メリット

### 2.1 コードレビューがしやすくなる

大きな1コミットや雑多な履歴を、意味のある単位に分割します。レビュアーは「スキーマ変更だけ」「API だけ」といった観点で差分を追えるため、理解コストと見落としが減ります。

### 2.2 履歴が「なぜそうしたか」を語れる

各コミットの説明を **「何を変えたか」ではなく「なぜ変えたか」** を重視するよう指示しています。後から `git log` を見たとき、設計意図や変更理由が追いやすい履歴になります。

### 2.3 作業の安全性が高い

履歴を書き換える作業は元に戻せないと怖いですが、このスキルは安全策を組み込んでいます。

| 仕組み | 効果 |
|--------|------|
| 作業前のコミットハッシュを記録 | 失敗時に `git reset --hard` で復旧可能 |
| `/tmp/original-diff.patch` に全差分を保存 | 組み替え前の内容を基準にできる |
| 最後にパッチ比較で検証 | 変更の欠落・意図しない改変を検出 |
| 未コミット変更・rebase 未完了を事前に中止 | 中途半端な状態での破壊的操作を防ぐ |

### 2.4 エージェントの挙動が安定・再現しやすい

スキルがないと、エージェントごとに分割粒度や順序、検証の有無がバラつきがちです。このスキルは **9ステップの固定フロー** なので、毎回同じ品質基準で履歴整理が行われます。

`GIT_EDITOR=true` を git コマンドに付ける指示は、エディタ待ちでエージェントが止まる問題を避ける実用的な工夫です。

### 2.5 論理的なコミット順序が保証される

「DB/スキーマ → バックエンド → フロントエンド」の順で TODO を立てるルールにより、依存関係に沿った積み上げになります。各コミットが単体で意味を持ち、問題のある変更を特定しやすくなります。

### 2.6 チーム開発の慣習に沿う

- 1コミット = 1論点
- レビュー単位が小さい
- main 上に rebase 済みであることを前提にする

といった、多くのチームが求める PR/レビュー文化に合った成果物が得られます。

## 3. スキルの配置場所

Cursor のスキルは **フォルダ名でスコープが決まります**。

### 3.1 ユーザーが置く場所

| 種類 | パス | スコープ |
|------|------|----------|
| **プロジェクト用** | `<プロジェクト>/.cursor/skills/rework-commits/SKILL.md` | そのリポジトリを開いたときだけ |
| **個人（グローバル）用** | `~/.cursor/skills/rework-commits/SKILL.md` | すべてのプロジェクト |

#### Windows での個人スキルパス（例）

```
C:\Users\<ユーザー名>\.cursor\skills\rework-commits\SKILL.md
```

#### プロジェクト用の例（mogura リポジトリ）

```
d:\dotinstall\mogura\.cursor\skills\rework-commits\SKILL.md
```

### 3.2 Cursor 組み込みスキル（触らない）

| フォルダ | 用途 |
|----------|------|
| `~/.cursor/skills-cursor/` | Cursor が自動管理する組み込みスキル |

**自分のスキルは `skills` に置き、`skills-cursor` には置かない** ようにしてください。

### 3.3 プロジェクト vs 個人の使い分け

| 置き場所 | 向いているケース |
|----------|------------------|
| `.cursor/skills/`（プロジェクト） | チームで Git 共有したい、プロジェクト固有のルール（ブランチ名、コミット順序など）がある |
| `~/.cursor/skills/`（個人） | どのプロジェクトでも同じ手順でコミット整理したい |

## 4. 利用手段（使い方）

### 4.1 前提

- Cursor で対象プロジェクトを開いていること
- Agent モードで依頼すること（Ask モードでは git 操作は実行されない）
- ブランチに未コミットの変更がないこと（スキルが事前にチェックして中止する）

### 4.2 依頼例

Cursor の Agent チャットで、例えば次のように依頼します。

```
rework-commits スキルに従って、このブランチのコミットを整理して
```

```
このブランチをレビューしやすいコミットに分割して。rework-commits スキルを使って。
```

エージェントが `.cursor/skills/` または `~/.cursor/skills/` 配下の `rework-commits/SKILL.md` を読み、手順に沿って作業します。

### 4.3 スキルが実行する手順（概要）

1. **未コミット変更の確認** — あれば中止
2. **rebase 状態の確認** — main 上でなければ中止
3. **復旧ポイントの保存** — 現在のコミットハッシュをユーザーに伝える
4. **元の diff を保存** — `/tmp/original-diff.patch`
5. **main に reset** — `git reset main` で変更を unstaged 状態に
6. **コミット計画** — 全変更を読み、TODO を `/tmp/split-todos.md` に記載
7. **コミット作成** — TODO を1つずつ実行、レビュー向けメッセージを付与
8. **検証** — 現在の diff と original-diff.patch を比較
9. **クリーンアップ** — 検証成功後、一時ファイルを削除

### 4.4 失敗時の復旧

検証に失敗した場合、スキルはユーザーに **作業開始前のコミットハッシュ** を伝えます。必要なら次で復旧できます。

```bash
git reset --hard <保存されていたコミットハッシュ>
```

---

## 5. いつ使うと効果的か

- 機能開発中に「とりあえず全部コミットした」ブランチを PR 前に整えたい
- レビュー指摘で「コミットを分けてほしい」と言われた
- 大きな変更を段階的にレビューしてもらいたい
- 履歴をきれいにしたいが、**変更内容自体は絶対に失いたくない**

---

## 6. 関連スキルとの違い

| スキル | 目的 |
|--------|------|
| **rework-commits** | 同一ブランチ内のコミット履歴を整理する |
| **split-to-prs**（Cursor 組み込み） | 作業を複数 PR に分割する（ユーザー承認必須） |

`rework-commits` は PR 分割より手軽に「レビュー可能な履歴」だけを得たい場面向けです。

---

## 7. 推奨事項（任意）

公式のスキル作成ガイドでは、`SKILL.md` 先頭に YAML frontmatter を付けるとエージェントがスキルを見つけやすくなります。

```yaml
---
name: rework-commits
description: Rework a branch into small semantic commits for review. Use when the user asks to split commits, reorganize commit history, or make a branch reviewable.
---
```

自動検出を強くしたい場合は frontmatter の追加を検討してください。
