## [VIEWを使用して売上レポート作成]

マイコード
```sql
CREATE VIEW sales_summary (store, year, month, sales) AS
SELECT
  s.store_id AS store,
  YEAR(p.payment_date) AS year,
  MONTH(p.payment_date) AS month,
  SUM(p.amount) AS sales
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id
GROUP BY s.store_id, YEAR(p.payment_date), MONTH(p.payment_date)
ORDER BY year, month;
```

---

### Copilotの評価

| 項目 | 評価 | コメント |
|------|------|----------|
| 結合の流れ | 正しい | `payment → staff → store_id` の流れでOK |
| 集計ロジック | 明快 | `YEAR()` + `MONTH()` で月別に集計 |
| ビューの定義 | 構文的に正しい | 列名も明示されていてGood |
| ORDER BY | ビュー内では**無意味** | ビューに `ORDER BY` を書いても**無視される**

### パフォーマンスが重くなる理由

### 1. **`YEAR()` や `MONTH()` による関数使用**

- `payment_date` にインデックスがあっても、**関数をかけるとインデックスが使えない**
- → **全件スキャンになりやすい**

### 2. **ビューは実行時に展開される**

- MySQLのビューは**仮想テーブル**で、**実行時に中身のクエリが展開される**
- → ビューを使うたびに**毎回集計が走る**ので、**キャッシュされない限り重くなる**

---

### 改善案1：`payment_date` に範囲指定できるようにする

ビューの中では `YEAR()` や `MONTH()` を使ってもOKだけど、  
**WHERE句で範囲指定できるようにしておくと、インデックスが効くようになる**

```sql
CREATE VIEW sales_summary AS
SELECT
  s.store_id AS store,
  p.payment_date AS payment_date,
  YEAR(p.payment_date) AS year,
  MONTH(p.payment_date) AS month,
  p.amount
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id;
```

→ そして、**使う側で集計する**：

```sql
SELECT
  store,
  YEAR(payment_date) AS year,
  MONTH(payment_date) AS month,
  SUM(amount) AS sales
FROM sales_summary
WHERE payment_date BETWEEN '2005-01-01' AND '2005-12-31'
GROUP BY store, year, month;
```

---

### 改善案2：マテリアライズドビュー的な処理（定期集計）

- MySQLには**正式なマテリアライズドビュー（実体を持つビュー）**はないけど、
- **定期的に集計結果を別テーブルにINSERTする**ことで、**高速な参照が可能になる**

```sql
CREATE TABLE sales_summary_materialized AS
SELECT
  s.store_id AS store,
  YEAR(p.payment_date) AS year,
  MONTH(p.payment_date) AS month,
  SUM(p.amount) AS sales
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id
GROUP BY s.store_id, YEAR(p.payment_date), MONTH(p.payment_date);
```

→ これを **定期的に更新**すれば、**ビューより圧倒的に高速**

---

### まとめ

| 問題点 | 内容 |
|--------|------|
| `YEAR()` / `MONTH()` の使用 | インデックスが効かず、全件スキャンになりやすい |
| ビューの `ORDER BY` | 効かない（ビューでは無視される） |
| ビューの性質 | 実行時に展開されるため、毎回集計が走る |

| 改善策 | 内容 |
|--------|------|
| 範囲指定できるようにする | `payment_date` をそのまま持たせておく |
| マテリアライズドビュー化 | 集計結果を別テーブルに保存しておく |

## [マテリアライズドビュー]

**マテリアライズドビュー的な処理を手動で行う場合、どうやって集計結果を更新するか**

> **必ずしも `DROP TABLE` する必要はないけど、**  
> **「既存のデータをどう扱うか」によって方法が変わる**

---

### 代表的な3つの更新方法

### 1 `DROP TABLE` → `CREATE TABLE`（完全再作成）

```sql
DROP TABLE IF EXISTS sales_summary_materialized;

CREATE TABLE sales_summary_materialized AS
SELECT ...
```

| 特徴 | 内容 |
|------|------|
| シンプル | テーブル構造も一緒に作り直せる |
| 注意点 | **権限・インデックス・制約・コメントなどが消える** |
| 向いてる場面 | 一時的な集計や開発中の用途に◎ |

---

### 2 `TRUNCATE TABLE` → `INSERT INTO`（構造を保ったまま全入れ替え）

```sql
TRUNCATE TABLE sales_summary_materialized;

INSERT INTO sales_summary_materialized
SELECT ...
```

| 特徴 | 内容 |
|------|------|
| テーブル構造・インデックスを保持 | `CREATE TABLE` で定義した構造を維持できる |
| 高速 | `TRUNCATE` は `DELETE` より速い |
| 向いてる場面 | **定期的な全更新**に最適 |

---

### 3 `INSERT ... ON DUPLICATE KEY UPDATE`（差分更新）

```sql
INSERT INTO sales_summary_materialized (store, year, month, sales)
SELECT ...
ON DUPLICATE KEY UPDATE
  sales = VALUES(sales);
```

| 特徴 | 内容 |
|------|------|
| 差分だけ更新できる | 既存データを保持しつつ更新 |
| 主キーやユニーク制約が必要 | `(store, year, month)` にユニーク制約が必要 |
| 向いてる場面 | **リアルタイム更新や部分更新**に◎ |

---

### 判断基準

| 目的 | 方法 | 理由 |
|------|------|------|
| 開発中・一時的な集計 | `DROP TABLE` → `CREATE TABLE` | 手軽でわかりやすい |
| 定期バッチ更新 | `TRUNCATE` → `INSERT` | 構造を保ちつつ高速 |
| 差分更新したい | `INSERT ... ON DUPLICATE KEY UPDATE` | 効率的だけど設計が必要 |

---

### まとめ

> **「DROP TABLE」は1つの手段だけど、毎回使う必要はない**  
> **更新の目的（全入れ替え or 差分更新）に応じて、最適な方法を選ぶのがベスト**
