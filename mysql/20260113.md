## [売上集計]

### `GROUP BY`を使った、店舗が増えても対応可能なパターン

```SQL
SELECT
  s.store_id,
  SUM(p.amount) AS total_sales
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id
GROUP BY s.store_id;
```
結果
```BASH
+----------+-------------+
| store_id | total_sales |
+----------+-------------+
|        1 |    33482.50 |
|        2 |    33924.06 |
+----------+-------------+
```

---

### `CASE式`を使った、店舗名をカラム名にした横列パターン

```SQL
SELECT
  SUM(CASE WHEN s.store_id = 1 THEN p.amount ELSE 0 END) AS store_1,
  SUM(CASE WHEN s.store_id = 2 THEN p.amount ELSE 0 END) AS store_2
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id;
```
結果
```BASH
+----------+----------+
| store_1  | store_2  |
+----------+----------+
| 33482.50 | 33924.06 |
+----------+----------+
```

今回の事例では`GROUP BY`を使ったパターンの方が実践向きといえる  

## [ジャンル別売上ランキング]

### ボトルネックが発生してタイムアウトしたコード

**エラーコード**
```SQL
SELECT
  c.name AS category,
  SUM(p.amount) AS sales
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id
JOIN inventory i ON s.store_id = i.store_id
JOIN film_category f ON i.film_id = f.film_id
JOIN category c ON f.category_id = c.category_id
GROUP BY c.category_id, c.name;
```

**内部結合の順序 payment - staff - inventory - film_category - category**  

`staff`から`inventory`の部分でボトルネックが発生  
結合順序と種類を**payment - rental - inventory - film_category - category**に変更した  

(ボトルネックの原因)  
結合のルートが適切ではなく、巨大な中間データが発生してしまっている。  
「１つの支払い(payment)」に対して「その店(store)にあるすべての在庫(inventory)」を紐づけている  
さらに論理的な誤り、「実際に貸し出した映画」ではなく「その店にある全映画」の売上を合算する動きになる  

**修正コード**
```sql
SELECT
  c.name as category,
  sum(p.amount) as sales
  -- RANK() OVER (ORDER BY SUM(p.amount) DESC) AS ranking   <- 非推奨
FROM payment p
JOIN rental r ON p.rental_id = r.rental_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film_category fc ON i.film_id = fc.film_id
JOIN category c ON fc.category_id = c.category_id
GROUP BY c.category_id, c.name
ORDER BY sales DESC;
```

ランキングを付ける場合は以上のように`RANK()`を使ってウィンドウ関数で表現できる  
しかしウィンドウ関数の中に集計関数を入れるのは推奨されていない  
MySQLではエラーは発生しないが、他のDBでは発生するかもしれない  

(非推奨理由)  
集計関数とウィンドウ関数を同じレベルで混ぜるとSQLの文法的に曖昧になりやすい  
`GROUP BY`とウィンドウ関数の評価タイミングが衝突することがある  

(対処方法)  
集計してから、その結果に対して`RANK()`をかけるのが王道  
つまりサブクエリや`WITH`で集計してから`RANK()`をかける  

**対処コード**(注:`RANK()`ではなく`ROW_NUMBER()`を使用した)
```SQL
WITH category_sales AS (
  SELECT
    c.name AS category,
    SUM(p.amount) AS sales
  FROM payment p
  JOIN rental r ON p.rental_id = r.rental_id
  JOIN inventory i ON r.inventory_id = i.inventory_id
  JOIN film_category fc ON i.film_id = fc.film_id
  JOIN category c ON fc.category_id = c.category_id
  GROUP BY c.category_id, c.name
)
SELECT
  category,
  sales,
  ROW_NUMBER() OVER (ORDER BY sales DESC) AS ranking
FROM category_sales;
```

## [インデックス解説]

### インデックスについてGeminiより抜粋

インデックス（索引）は、データベースのパフォーマンスを支える最も重要な仕組みの一つです。初心者の方にもわかりやすく、身近な例えで解説しますね。

---

## 1. インデックスとは「本の索引」や「辞書の索引」のこと

インデックスがない状態でデータを探すのは、**「索引がない500ページの本から、特定の単語を1ページずつめくって探す（全ページスキャン）」**のと同じです。

一方、インデックスがある状態は、**「本の巻末にある索引を見て、その単語が何ページにあるかを確認してから、そのページを直接開く」**という動作になります。

### JOINのキーにインデックスがあるとは？

前回のクエリの `ON p.rental_id = r.rental_id` を例にしましょう。

1. **インデックスがない場合：**
`payment`テーブルの1行目を見る → その `rental_id` を探すために、`rental`テーブルの**端から端まで全部**チェックする。これを数万回繰り返します。これが「タイムアウト」の原因です。
2. **インデックスがある場合：**
`payment`テーブルの1行目を見る → `rental`テーブルの**「索引（インデックス）」**を使って、対象の行がどこにあるか一瞬で特定する。

---

## 2. インデックスの状態を調べる方法

MySQLで「インデックスが貼られているか」を確認する方法は主に3つあります。

### 方法①：`SHOW INDEX` 命令を使う（一番確実）

特定のテーブルにどのようなインデックスがあるか一覧で確認できます。

```sql
SHOW INDEX FROM rental;

```

* **ここをチェック！**
* `Column_name`: どの列にインデックスがあるか。
* `Key_name`: インデックスの名前（`PRIMARY` は主キー、それ以外は後から貼られたもの）。



### 方法②：`DESC` 命令を使う（手軽）

テーブルの構造を確認するコマンドですが、インデックスの有無もわかります。

```sql
DESC rental;

```

* **ここをチェック！**
* `Key` という列を見ます。
* **PRI**: Primary Key（主キー）。自動的に最強のインデックスが貼られています。
* **MUL**: Multiple（索引）。その列にインデックスが貼られています。
* **UNI**: Unique。重複を許さないインデックスが貼られています。



### 方法③：`EXPLAIN` を使う（クエリ実行時の状態を見る）

実際にクエリを動かす前に、MySQLがインデックスを使ってくれるかどうかを確認できます。

```sql
EXPLAIN SELECT * FROM rental WHERE inventory_id = 10;

```

* **ここをチェック！**
* `possible_keys`: 使える可能性のあるインデックス。
* `key`: **実際に使われるインデックス。** ここが `NULL` だと、インデックスが使われず遅い（フルスキャン）ということです。



---

## 3. なぜSakilaでは最初から速いのか？

Sakilaのような練習用データベースでは、あらかじめ「よく結合に使う列（IDなど）」にはインデックスが設定されています。

しかし、前回のタイムアウトの例のように、**「論理的に遠回りな結合」**をしてしまうと、MySQLが「どのインデックスを使えばいいかわからない」状態になったり、インデックスがあっても処理しきれないほど膨大な組み合わせ（デカルト積）が発生したりしてしまいます。

> **ポイント：**
> 「インデックスがある列をJOINのキーに使う」ことと、「テーブル同士を正しい親子関係でつなぐ」ことの両方が揃って初めて、SQLは爆速になります。
