## [INDEX]

### INDEXの確認と操作

テーブルとデータ読み込み
```sql
drop table if exists posts;
CREATE TABLE posts (
  id       INT NOT NULL AUTO_INCREMENT,
  message  VARCHAR(140),
  likes    INT,
  area     VARCHAR(20),
  PRIMARY KEY(id)
);

LOAD DATA LOCAL INFILE 'D:/MySQL_sakila/data.csv' INTO TABLE posts
  FIELDS TERMINATED BY ','
  LINES TERMINATED BY '\n'
  IGNORE 1 LINES
  (message, likes, area);
```

---

### `posts`テーブルのインデックスを確認
```sql
SHOW INDEX FROM posts\G
```
#### 末尾の`\G`は結果の省略形を指定、Gは必ず大文字で、最後に`;`は入れない

結果
```Bash
*************************** 1. row ***************************
        Table: posts
   Non_unique: 0
     Key_name: PRIMARY
 Seq_in_index: 1
  Column_name: id
    Collation: A
  Cardinality: 200
     Sub_part: NULL
       Packed: NULL
         Null:
   Index_type: BTREE
      Comment:
Index_comment:
      Visible: YES
   Expression: NULL
1 row in set (0.00 sec)
```
#### 確認するところは`Key_name`と`Column_name`  
カラム`id`にインデックスがあることがわかる  

---
### `EXPLAIN`を使ってインデックスが`id`のみの状態で`id`に検索をかける
```sql
EXPLAIN SELECT * FROM posts WHERE id = 30\G
```
結果
```Bash
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: posts
   partitions: NULL
         type: const
possible_keys: PRIMARY
          key: PRIMARY
      key_len: 4
          ref: const
         rows: 1
     filtered: 100.00
        Extra: NULL
1 row in set, 1 warning (0.00 sec)
```
#### 確認するところは`key`と`rows`  
`key`は`PRIMARY`でインデックスが効いていて  
`rows`は`1`で1つしか見に行っていない  
つまり効率のよい検索が行われている  

----
### `EXPLAIN`を使ってインデックスが`id`のみの状態で`erea`に検索をかける
```sql
EXPLAIN SELECT * FROM posts WHERE area = 'kyoto'\G
```
結果
```Bash
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: posts
   partitions: NULL
         type: ALL
possible_keys: NULL
          key: NULL
      key_len: NULL
          ref: NULL
         rows: 200
     filtered: 10.00
        Extra: Using where
1 row in set, 1 warning (0.00 sec)
```
#### 確認するところは`key`と`rows`  
`key`は`NULL`でインデックスが無い  
`rows`は`200`ですべての値を見に行っている(値は全部で`200`
の設定でテストしている)  
つまり効率の悪い検索が行われている  


---
### `area`にインデックスを設定する
設定コード
```sql
ALTER TABLE posts ADD INDEX index_area(area);
```
`ALTER TABLE`を使って`ADD INDEX`でインデックスを設定  
`index_area`はインデックス名、()内に対象のカラム名を指定  

`SHOW INDEX FROM posts\G`でインデックスを確認
```Bash
*************************** 1. row ***************************
        Table: posts
   Non_unique: 0
     Key_name: PRIMARY
 Seq_in_index: 1
  Column_name: id
    Collation: A
  Cardinality: 200
     Sub_part: NULL
       Packed: NULL
         Null:
   Index_type: BTREE
      Comment:
Index_comment:
      Visible: YES
   Expression: NULL
*************************** 2. row ***************************
        Table: posts
   Non_unique: 1
     Key_name: index_area
 Seq_in_index: 1
  Column_name: area
    Collation: A
  Cardinality: 15
     Sub_part: NULL
       Packed: NULL
         Null: YES
   Index_type: BTREE
      Comment:
Index_comment:
      Visible: YES
   Expression: NULL
2 rows in set (0.00 sec)
```
`area`にインデックスが設定されている  

`EXPLAIN SELECT * FROM posts WHERE area = 'kyoto'\G`を実行  
```Bash
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: posts
   partitions: NULL
         type: ref
possible_keys: index_area
          key: index_area
      key_len: 83
          ref: const
         rows: 1
     filtered: 100.00
        Extra: NULL
1 row in set, 1 warning (0.00 sec)
```
`key`に`index_area`が設定されていて、`rows`が`1`になって効率化が図られた  

---

### `area`からインデックスを外す
```sql
ALTER TABLE posts DROP INDEX index_area;
```
`ALTER TABLE`を使って`DROP INDEX`でインデックス設定を削除  

---

### まとめ
- パフォーマンスが落ちてきたら必ず`EXPLAIN`で調査を行う
- 注意点としてインデックスを設定するとデータベースの容量は大きくなる
- 内容やデータ量などを勘案してインデックス設定を行う
- 適切なインデックス設定が全体のパフォーマンスを上げることになる
