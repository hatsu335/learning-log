## [同じジャンルばかり借りる顧客]

### `COUNT(DISTINCT c.category_id)`で重複を解消(このコードの心臓部)

最初のコード
```sql
SELECT
  ct.customer_id AS ct_id,
  ct.first_name AS f_name,
  ct.last_name AS l_name,
  -- DISTINCTで重複を解消して純粋なジャンル数に
  COUNT(DISTINCT c.category_id) AS c_kinds,
  COUNT(r.rental_id) AS r_num,
  -- レンタル癖を数値化
  ROUND(
    COUNT(r.rental_id) / 
    (COUNT(DISTINCT c.category_id) * COUNT(r.rental_id)), 2)
    AS cat_rate
FROM customer ct
JOIN rental r ON ct.customer_id = r.customer_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film_category fc ON i.film_id = fc.film_id
JOIN category c ON fc.category_id = c.category_id
GROUP BY ct.customer_id, ct.first_name, ct.last_name
ORDER BY cat_rate DESC;
```

### 1. 数式の検証（数学的な整理）

現在の式だと「レンタルを1回しかしていない人」も「100回している人」も、**ジャンル数が同じなら同じ値**になってしまう  
「同じジャンルを繰り返し借りる（こだわりが強い）」という特徴を出すには、少しもったいない  
また、`cat_rate`の数値を見ても直観的にわかりにくい指標になっている  

---

### 2. より「こだわり」を可視化する指標

「同じジャンルばかり選ぶ人の特徴」を数値化する2つのアプローチ

### A. 1ジャンルあたりの平均レンタル数（密度）

「1つのジャンルに対して、どれだけ深くハマっているか」を出す指標  

* **数式:** `COUNT(r.rental_id) / COUNT(DISTINCT c.category_id)`
* **意味:** 1ジャンルあたり何回レンタルしたか。数値が高いほど、特定のジャンルをリピートしている  

### B. ジャンル専念度（特化率）

今回の目的である「同じジャンルだけ借りる人」を1.0（100%）として評価する指標  

* **数式:** `1 / COUNT(DISTINCT c.category_id)`
* **意味:** 数値が1に近いほど、浮気をせずに特定のジャンルに絞っている  

---

### 3. 改定版

「1ジャンルあたりのレンタル密度」を導入し、さらに「1回しか借りていないビギナー」を除外して「常連のこだわり派」を抽出できるように改良  

```sql
SELECT
  ct.customer_id AS ct_id,
  ct.first_name AS f_name,
  ct.last_name AS l_name,
  COUNT(DISTINCT c.category_id) AS c_kinds,
  COUNT(r.rental_id) AS r_num,
  -- 1ジャンルあたり何回借りているか（こだわり度）（密度）
  ROUND(COUNT(r.rental_id) / COUNT(DISTINCT c.category_id), 2) AS genre_density,
  -- どれくらいジャンルを絞っているか（1に近いほど単一ジャンル派）（特化率）
  ROUND(1 / COUNT(DISTINCT c.category_id), 2) AS focus_rate
FROM customer ct
JOIN rental r ON ct.customer_id = r.customer_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film_category fc ON i.film_id = fc.film_id
JOIN category c ON fc.category_id = c.category_id
GROUP BY ct.customer_id, ct.first_name, ct.last_name
-- 分析の精度を上げるため、例えば20回以上借りている人に限定
HAVING r_num >= 20
ORDER BY genre_density DESC, r_num DESC;
```

## [データベースの役割とは]

MySQLの学習が進んでくると、「どこまでをDBに任せるべきか？」という疑問が湧いてくる  
Pythonなどのアプリケーションコードと、データベースの役割分担は、設計の肝とも言える  

---

### 一般的な役割分担の考え方

#### **データベース（MySQLなど）が担うべき役割**
- **データの永続化**：マスタデータやトランザクションデータの保存
- **データの整合性の担保**：主キー・外部キー制約、NOT NULL、UNIQUEなど
- **検索・集計処理**：`SELECT`文、`JOIN`、`GROUP BY`、`ORDER BY`など
- **バッチ処理や定型処理**：ストアドプロシージャやトリガーで一部自動化
- **アクセス制御**：ユーザーごとの権限設定

#### **アプリケーション（PythonやJavaなど）が担うべき役割**
- **ビジネスロジックの実装**：業務ルールに基づく処理（例：在庫が0なら注文不可）
- **ユーザーインターフェースの提供**：GUIやWeb画面など
- **外部サービスとの連携**：API呼び出し、ファイル操作など
- **柔軟なデータ加工や表示**：複雑なロジックや条件分岐を含む処理

---

### 実際の現場では？

現場では「**データベースはデータの管理と効率的な検索に集中させる**」という考え方が主流  

- **マスタ情報やトランザクションデータはDBに保存**。
- **検索や集計はSQLで行う**（パフォーマンスが良いから）。
- **業務ロジックや画面表示に関する処理はアプリ側で実装**。

ただし、**定型的な集計やチェック処理**（例：在庫の自動更新、ログの記録など）は、**ストアドプロシージャやトリガー**でDB側に持たせることもある  

---

### まとめ

全部をDBに詰め込むと、保守性が下がったり、他の言語やシステムと連携しづらくなったりすることもある  
逆に、すべてをアプリ側でやると、パフォーマンスが悪くなったり、SQLが複雑になったりする

こんなバランスが理想的か

| 処理内容 | 実装場所 | 理由 |
|----------|------------------|------|
| マスタデータの保存・取得 | MySQL | データの一元管理と整合性のため |
| 複雑な集計（売上月別集計など） | MySQL（SQL） | パフォーマンスが高い |
| 業務ルール（例：割引条件） | Pythonなどアプリ側 | ロジックの変更がしやすい |
| UI操作やファイル出力 | Pythonなどアプリ側 | DBでは対応しづらい |
