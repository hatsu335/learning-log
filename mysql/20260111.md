## [INFORMATION_SCHEMA]

### `DESC テーブル`より簡潔に表示

`INFORMATION_SCHEMA`は読み取り専用のメタ情報ビュー  
開発者・DBA向けで、テーブル構造、カラム情報、制約、インデックスなど確認できる

**`COLUMN名`と`DATA TYPE`のみの表示方法**

```sql
SELECT column_name, data_type
FROM information_schema.columns
WHERE `TABLE_SCHEMA` = 'sakila' AND `TABLE_NAME` = 'actor';
```

結果
```BASH
+-------------+-----------+
| COLUMN_NAME | DATA_TYPE |
+-------------+-----------+
| actor_id    | smallint  |
| first_name  | varchar   |
| last_name   | varchar   |
| last_update | timestamp |
+-------------+-----------+
```

**`INFORMATION_SCHEMA`で確認できる主なこと

| 確認したいこと | テーブル名 | 内容の例 |
|----------------|------------|----------|
| テーブル一覧 | `TABLES` | テーブル名、行数、ストレージ情報など |
| カラム情報 | `COLUMNS` | カラム名、データ型、NULL許可、デフォルト値など |
| インデックス | `STATISTICS` | インデックス名、対象カラム、ユニークかどうかなど |
| 主キー・外部キーなどの制約 | `KEY_COLUMN_USAGE`, `TABLE_CONSTRAINTS` | 主キーや外部キーの関係 |
| ビュー情報 | `VIEWS` | ビューの定義 |
| ストアドプロシージャ・関数 | `ROUTINES` | 名前、型、定義など |
| トリガー | `TRIGGERS` | トリガーのイベントやタイミング |
| ユーザー権限 | `USER_PRIVILEGES`, `SCHEMA_PRIVILEGES` | 誰が何の操作をできるか |

---

### 具体例

1. データベース内の全テーブル一覧

```sql
SELECT table_name
FROM INFORMATION_SCHEMA.TABLES
WHERE table_schema = 'sakila';
```

2. 特定テーブルのインデックス情報

```sql
SELECT index_name, column_name, non_unique
FROM INFORMATION_SCHEMA.STATISTICS
WHERE table_schema = 'sakila' AND table_name = 'film';
```

3. 外部キーの参照関係を調べる

```sql
SELECT table_name, column_name, referenced_table_name, referenced_column_name
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE table_schema = 'sakila' AND referenced_table_name IS NOT NULL;
```

4. NULLを許容しないカラム一覧

```sql
SELECT table_name, column_name
FROM INFORMATION_SCHEMA.COLUMNS
WHERE table_schema = 'sakila' AND is_nullable = 'NO';
```

### 使いこなすコツ

- `TABLE_SCHEMA` で対象のデータベースを絞るのが基本
- `LIKE` や `IN` を使って柔軟に検索できる
- GUIツールがなくても、**構造を把握して安全に操作できる**のが最大の強み

## [一度も借りられていない映画を抽出]

### マイコード

```sql
SELECT
  f.film_id,
  f.title
FROM film f
LEFT JOIN
(SELECT
  f.film_id,
  f.title
FROM rental r 
JOIN inventory i ON r.inventory_id = i.inventory_id
LEFT JOIN film f ON i.film_id = f.film_id
GROUP BY film_id) af
ON af.film_id = f.film_id
WHERE af.film_id IS NULL;
```

**改善ポイント**

- `film`テーブル基準で結合していく
- サブクエリの`GROUP BY`は不要(存在確認だけでOK)
- `LEFT JOIN`の中で`JOIN`を重ねているが`NOT EXISTS`を使えば明快に

### 改善コード

```sql
SELECT
  f.film_id,
  f.title
FROM film f 
WHERE NOT EXISTS (
    SELECT 1
    FROM inventory i  
    JOIN rental r ON i.inventory_id = r.inventory_id
    WHERE f.film_id = i.film_id
);
```

## [`NOT EXISTS`の基本構文] ChatGPTより抜粋

```sql
SELECT 列
FROM 外側のテーブル t
WHERE NOT EXISTS (
    SELECT 1
    FROM 内側のテーブル s
    WHERE 条件
);
```

**意味**

> 「内側の SELECT が **1行も返さない場合だけ**、外側の行を返す」

---

### 1. EXISTS / NOT EXISTS の本質

**EXISTS の評価ルール**

* 内側の SELECT の **結果セットの中身は見ない**
* **1行でも返れば TRUE**
* 0行なら FALSE

```sql
EXISTS (SELECT ...)
```

| 内側の結果 | 評価    |
| ----- | ----- |
| 0行    | FALSE |
| 1行以上  | TRUE  |

```sql
NOT EXISTS (SELECT ...)
```

| 内側の結果 | 評価    |
| ----- | ----- |
| 0行    | TRUE  |
| 1行以上  | FALSE |

---

### 2. sakila の例で構文を分解する

あなたのクエリ：

```sql
SELECT
  f.film_id,
  f.title
FROM film f 
WHERE NOT EXISTS (
    SELECT 1
    FROM inventory i  
    JOIN rental r ON i.inventory_id = r.inventory_id
    WHERE f.film_id = i.film_id
);
```

### ① 外側クエリ

```sql
FROM film f
```

→ **1本ずつ映画を取り出す**

---

### ② 内側クエリ（相関サブクエリ）

```sql
SELECT 1
FROM inventory i  
JOIN rental r ON i.inventory_id = r.inventory_id
WHERE f.film_id = i.film_id
```

ここが重要です。

#### このサブクエリが探しているもの

> 「この film に紐づく inventory が
> **1回でも rental に登場したことがあるか？**」

* `JOIN rental` している時点で

  * **借りられた inventory しか出てこない**
* `f.film_id = i.film_id`

  * 外側の film と紐付け（＝相関）

---

### ③ NOT EXISTS の判定

| 状況          | 内側   | NOT EXISTS |
| ----------- | ---- | ---------- |
| 一度も借りられていない | 0行   | TRUE（表示）   |
| 1回でも借りられた   | 1行以上 | FALSE（除外）  |

---

### 3. なぜ `SELECT 1` なのか？

```sql
SELECT 1
SELECT *
SELECT i.film_id
```

**どれでも結果は同じ**です。

### 理由

* EXISTS は「行があるか」しか見ない
* 列の値は一切評価されない

### 慣習的ベストプラクティス

```sql
SELECT 1
```

* 意味が明確
* 無駄な列を読まない（実行計画上も有利）

---

### 4. `NOT EXISTS` が LEFT JOIN より安全な理由

### NULL に影響されない

```sql
NOT IN (SELECT ...)
```

は **NULL が1つでもあると全滅**しますが、

```sql
NOT EXISTS
```

は **NULL を論理的に正しく扱う**

---

### 5. NOT EXISTS の典型パターン

### ① 一度も〜されていない

```sql
WHERE NOT EXISTS (
  SELECT 1
  FROM 子テーブル
  WHERE 子.外部キー = 親.id
)
```

### ② 重複チェック

```sql
WHERE EXISTS (
  SELECT 1
  FROM table2
  WHERE table2.col = table1.col
)
```

### ③ 条件付き否定

```sql
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
    AND o.status = 'CANCEL'
)
```

---

### 6. 実行イメージ（重要）

**映画1本ごとに**以下を評価：

```text
この映画に対して
  └ rental が1行でも存在する？
      ├ YES → 除外
      └ NO  → 採用
```

👉 **「1件でもあればアウト」系条件に最適**

---

### 7. パフォーマンス面の補足（MySQL）

* MySQL は `NOT EXISTS` を **セミジョイン**に最適化
* 適切なインデックスがあれば非常に高速

### 推奨インデックス

```sql
inventory(film_id)
rental(inventory_id)
```

---

### 8. まとめ（要点）

| 項目         | ポイント            |
| ---------- | --------------- |
| NOT EXISTS | 内側が0行なら TRUE    |
| SELECT句    | 何を書いてもよい（慣習は 1） |
| 相関         | 外側の行ごとに評価       |
| 用途         | 「一度も〜されていない」    |
| 安全性        | NULL の影響を受けない   |

## [`NOT EXISTS` と `NOT IN` の決定的な違い] ChatGPT抜粋

### 1.1 見た目は似ているが、論理が違う

### NOT IN の例

```sql
SELECT f.film_id, f.title
FROM film f
WHERE f.film_id NOT IN (
    SELECT i.film_id
    FROM inventory i
    JOIN rental r ON i.inventory_id = r.inventory_id
);
```

一見すると `NOT EXISTS` と同じ意味に見えます。

---

### 1.2 NOT IN が危険な理由（NULL問題）

`NOT IN` は **三値論理（TRUE / FALSE / UNKNOWN）** の影響を受けます。

### 内側の結果に NULL が1つでも含まれると？

```text
f.film_id NOT IN (1, 2, NULL)
```

→ **すべて UNKNOWN**
→ **結果が1行も返らない**

### sakila では？

* 外部キー制約があるため今回は起きにくい
* しかし **実務では非常に頻発する事故要因**

---

### 1.3 論理的な違いを比較

| 観点     | NOT EXISTS | NOT IN       |
| ------ | ---------- | ------------ |
| NULL耐性 | 強い         | 弱い           |
| 意味     | 行の存在否定     | 値の集合比較       |
| 可読性    | 高い（存在チェック） | 直感的だが危険      |
| 実務推奨   | ◎          | △（NULL保証時のみ） |

👉 **「存在しないこと」を表したいなら NOT EXISTS 一択**

### 2. `EXPLAIN` で見る NOT EXISTS の動作

SQL は「書いた通り」には実行されません。
**実行計画（EXPLAIN）を読む力**が重要です。

---

### 2.1 EXPLAIN の基本

```sql
EXPLAIN
SELECT
  f.film_id,
  f.title
FROM film f 
WHERE NOT EXISTS (
    SELECT 1
    FROM inventory i  
    JOIN rental r ON i.inventory_id = r.inventory_id
    WHERE f.film_id = i.film_id
);
```

---

### 2.2 注目すべきカラム

| カラム         | 意味         |
| ----------- | ---------- |
| select_type | クエリの役割     |
| type        | テーブルアクセス方法 |
| key         | 使用インデックス   |
| rows        | 推定行数       |
| Extra       | 最重要        |

---

### 2.3 `DEPENDENT SUBQUERY` の意味

MySQL 8 以前では、よく以下が出ます。

```text
select_type: DEPENDENT SUBQUERY
```

### 意味

* 外側の film 1行ごとに
* 内側のサブクエリが評価される

👉 **相関サブクエリであることを示す**

---

### 3. MySQL の最適化（セミジョイン）

重要な事実です。

### 見た目は相関サブクエリだが…

MySQL は以下のように **内部で変形**します。

```sql
NOT EXISTS (subquery)
↓
ANTI SEMI JOIN
```

### 結果

* 実行回数は激減
* LEFT JOIN + GROUP BY より高速なことが多い

👉 **「相関＝遅い」は誤解**

---

### 4. LEFT JOIN + HAVING との比較

### 同じ意味の別解

```sql
SELECT f.film_id, f.title
FROM film f
JOIN inventory i ON f.film_id = i.film_id
LEFT JOIN rental r ON i.inventory_id = r.inventory_id
GROUP BY f.film_id, f.title
HAVING COUNT(r.rental_id) = 0;
```

---

### 4.1 比較表

| 観点   | NOT EXISTS | LEFT JOIN + HAVING |
| ---- | ---------- | ------------------ |
| 可読性  | 高い         | やや低い               |
| バグ耐性 | 高い         | GROUP BYミス注意       |
| 拡張性  | 高い         | 条件追加が煩雑            |
| 実務   | ◎          | ○                  |

---

### 5. NOT EXISTS を使うべき典型判断基準

以下に当てはまれば **NOT EXISTS を選ぶ**べきです。

* 「一度も〜されていない」
* 「該当レコードが存在しない」
* 「1件でもあったら除外」

---

### 6. 実務でよくある誤解

### 誤解①：SELECT 1 だと遅い？

→ **完全な誤解**
→ EXISTS は列を評価しない

---

### 誤解②：相関サブクエリは使わない方がいい？

→ **最適化前提なら問題なし**

---

### 誤解③：JOIN の方が SQL っぽい？

→ **論理表現としては EXISTS の方が正確な場合が多い**
