## [`SHOW INDEX FROM テーブル名`]

### テーブルに定義されているインデックスの情報を確認するためのコマンド

**SQLの実行効率を上げるための分析や設計に欠かせない**

`SHOW INDEX FROM テーブル名;` で得られる主な情報

| カラム名 | 意味 | よく見るポイント |
|----------|------|------------------|
| `Table` | 対象のテーブル名 | 確認用 |
| `Non_unique` | 0ならユニークインデックス | 主キーや一意制約の確認に使う |
| `Key_name` | インデックス名 | `PRIMARY` や `idx_...` など |
| `Seq_in_index` | インデックス内のカラム順序 | 複合インデックスの順番確認に重要 |
| `Column_name` | インデックス対象のカラム名 | どのカラムにインデックスがあるか |
| `Collation` | 昇順（A）か降順（D）か | MySQL 8.0以降で有効 |
| `Cardinality` | インデックス内の一意な値の推定数 | 選択性の目安（高いほど良い） |
| `Index_type` | BTREE, FULLTEXT, HASH など | インデックスの種類 |
| `Comment` | 補足情報 | 特殊なインデックスの説明など |

---

**パフォーマンス改善のための分析**

- クエリが遅いときに「**インデックスが効いているか？**」を確認
- `EXPLAIN` と組み合わせて「**どのインデックスが使われているか**」を調べる

**インデックスの設計・見直し**

- 複合インデックスの順序が正しいか確認（`Seq_in_index`）
- 不要なインデックスがないかチェック（重複や未使用）

**ユニーク制約や主キーの確認**

- `Non_unique = 0` なら一意性が保証されている
- `Key_name = PRIMARY` で主キーを確認

**選択性の確認**

- `Cardinality` が高いほど、インデックスの効果が高い
- 逆に低いと「インデックスを使っても意味がない」こともある

---

### `sakila`の`rental`の例

結果を見て以下のような情報を確認

- `rental_date` にインデックスがあるか？

- `Cardinality` を見て、どのカラムが選択性高いか？

---

### まとめ

| ポイント | 内容 |
|----------|------|
| 何がわかる？ | インデックスの構造・種類・順序・選択性など |
| いつ使う？ | クエリ最適化、インデックス設計、パフォーマンス分析時 |
| 補足 | `EXPLAIN` とセットで使うと効果倍増！ |

## [複合インデックスとは]

### **複合インデックスの順番確認**っていうのは、**複数のカラムで作られたインデックスが、どの順番で並んでいるかを確認すること**

**クエリのパフォーマンスにかなり影響する重要ポイント**

---

このようなインデックスを作ったとする
```sql
CREATE INDEX idx_customer_rental ON rental (customer_id, rental_date);
```

これは「`customer_id` と `rental_date` の**複合インデックス**」で、**`customer_id` → `rental_date` の順番で並んでいる**という意味

---

### なぜ順番が重要なのか

インデックスは**先頭のカラムから順に使われる**から

### 例：上のインデックスで使えるクエリ

| クエリ | インデックス使える？ | 理由 |
|--------|----------------------|------|
| `WHERE customer_id = 1` | 〇 使える | 先頭カラムが条件にある |
| `WHERE customer_id = 1 AND rental_date = '2022-01-01'` | 〇 使える | 両方のカラムが順に使われている |
| `WHERE rental_date = '2022-01-01'` | × 使えない | 先頭の `customer_id` が条件にない |

---

### `SHOW INDEX` で順番を確認する

```sql
SHOW INDEX FROM rental;
```

出力例

| Key_name           | Seq_in_index | Column_name   |
|--------------------|--------------|---------------|
| idx_customer_rental | 1            | customer_id   |
| idx_customer_rental | 2            | rental_date   |

`Seq_in_index` が **1 → 2** になってるのが**インデックスの順番**

---

### 活用する場面

- クエリが遅いとき、「**インデックスはあるのに効いてない**」と感じたら、**順番が合ってるか確認**
- よく使う検索条件の順番に合わせてインデックスを設計するのがコツ

---

### まとめ

| 項目 | 内容 |
|------|------|
| 複合インデックスの順番 | `Seq_in_index` で確認できる |
| 順番が合わないと？ | インデックスが効かず、全件スキャンになることも |
| 設計のコツ | よく使う検索条件の順に並べるのが基本 |

## [`EXPLAIN`]

### 出力の見方（主なカラム）

| カラム名 | 意味 | 注目ポイント |
|----------|------|--------------|
| `id` | 実行順序 | 小さいほど外側のクエリ |
| `select_type` | 単純 or サブクエリなど | 通常は `SIMPLE` |
| `table` | 対象テーブル名 | 結合順に並ぶ |
| `type` | アクセス方法 | **ALL（全件走査）は要注意** |
| `possible_keys` | 利用可能なインデックス | 候補が出てるか確認 |
| `key` | 実際に使われたインデックス | ここが `NULL` だとインデックス未使用 |
| `rows` | 読み込む行数の見積もり | 大きいほど重い |
| `Extra` | 補足情報 | `Using where`, `Using index`, `Using temporary` など |


| 状態 | 見るべきポイント |
|------|------------------|
| インデックスが効いていない | `type = ALL`, `key = NULL` |
| 結合が重い | `rows` が多い、`Using temporary` や `Using filesort` が出る |
| 効いている | `type = ref` や `eq_ref`、`Using index` が出る |

---

### 先日のタイムアウトしたクエリに `EXPLAIN` をつけた

```sql
EXPLAIN
SELECT
  c.name AS category,
  SUM(p.amount) AS sales
FROM payment p
JOIN staff s ON p.staff_id = s.staff_id
JOIN inventory i ON s.store_id = i.store_id
JOIN film_category f ON i.film_id = f.film_id
JOIN category c ON f.category_id = c.category_id
GROUP BY c.category_id, c.name;
```

### 読み解きポイント

| table | type  | key                  | rows | Extra                        | コメント |
|-------|-------|----------------------|------|------------------------------|----------|
| `s`   | index | `idx_fk_store_id`    | 2    | Using index; Using temporary |  スタッフは2人だけ。問題なし |
| `i`   | ref   | `idx_store_id_film_id` | 2290 | Using index                  |  ここが**重いポイント**！ |
| `f`   | ref   | `PRIMARY`            | 1    | Using index                  | OK       |
| `c`   | eq_ref| `PRIMARY`            | 1    |                              | OK       |
| `p`   | ref   | `idx_fk_staff_id`    | 8043 |                              |  ここもやや重いかも         |

---

### 問題の本質：`inventory i` の結合

```sql
JOIN inventory i ON s.store_id = i.store_id
```

この結合は、**「スタッフの所属店舗」と「在庫の店舗ID」を結んでいる**だけ  
つまり、**全在庫（2290件）をスタッフ2人に対して結合している**状態

→ 結果として、**2290 × 2 = 約4600行の中間表**ができてしまう

---

### `payment` の結合も非効率

```sql
JOIN payment p ON p.staff_id = s.staff_id
```

- `payment` は約8000件
- これが `staff_id` で結ばれているけど、**在庫との関連が弱い**
- 結果として、**「在庫 × 支払い」のような無関係な組み合わせが発生しやすい**

---

### 正しい結合にした場合の理想的な出力例

```sql
EXPLAIN
SELECT
  c.name AS category,
  SUM(p.amount) AS sales
FROM payment p
JOIN rental r ON p.rental_id = r.rental_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film_category f ON i.film_id = f.film_id
JOIN category c ON f.category_id = c.category_id
GROUP BY c.category_id, c.name;
```

| id | table     | type | key           | rows   | Extra              |
|----|-----------|------|---------------|--------|--------------------|
| 1  | p         | ALL  | PRIMARY       | 16000  |                    |
| 1  | r         | ref  | rental_id     | 1      | Using index        |
| 1  | i         | ref  | inventory_id  | 1      | Using index        |
| 1  | f         | ref  | film_id       | 1      | Using index        |
| 1  | c         | eq_ref | PRIMARY     | 1      |                    |

### この構造のメリット

ここでは `ref` や `eq_ref` が使われていて、**インデックスが効いている状態**  
`rows` も少なく、`Using index` が出ていればさらに良い感じ

`payment` → `rental` → `inventory` とたどることで、**実際にレンタルされた在庫だけに絞られる**

結果として、**中間表のサイズが激減し、結合効率が大幅に向上**

---

### もう一つ例として問題のあるケース

| id | table     | type | key     | rows   | Extra              |
|----|-----------|------|---------|--------|--------------------|
| 1  | s         | ALL  | PRIMARY | 2      |                    |
| 1  | i         | ALL  | store_id | 4581   | Using where        |
| 1  | p         | ref  | staff_id | 16000  | Using where        |

ここで `i`（inventory）が `ALL` になっていたら、**全件スキャンしてる証拠**  
`key` に `store_id` が出ていても、**結合条件が非効率だと使われないことがある**  

---

### まとめ

| 問題点 | 内容 |
|--------|------|
| `staff → inventory` の結合 | 店舗単位で全在庫を結ぶため、巨大な中間表ができる |
| `payment` の結合 | 在庫と直接関係がないため、無駄な組み合わせが発生 |
| 解決策 | `payment → rental → inventory` の正しい経路で結合する |

## [店舗ごとのジャンル別売上とレンタル件数のランキング]

```sql
WITH sales_row AS (
SELECT
  c.name AS category,
  SUM(CASE WHEN i.store_id = 1 THEN amount ELSE 0 END) AS store_1,
  COUNT(CASE WHEN i.store_id = 1 THEN p.rental_id ELSE NULL END) AS store_1_num,
  SUM(CASE WHEN i.store_id = 2 THEN amount ELSE 0 END) AS store_2,
  COUNT(CASE WHEN i.store_id = 2 THEN p.rental_id ELSE NULL END) AS store_2_num
FROM payment p
JOIN rental r ON p.rental_id = r.rental_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film_category fc ON i.film_id = fc.film_id
JOIN category c ON fc.category_id = c.category_id
GROUP BY c.category_id, c.name)
SELECT
  category,
  store_1,
  store_1_num,
  RANK() OVER (ORDER BY store_1_num DESC) AS ranking_1,
  store_2,
  store_2_num,
  RANK() OVER (ORDER BY store_2_num DESC) AS ranking_2
FROM sales_row
ORDER BY ranking_1;
```

### コメント

`COUNT()`の中の`CASE式`について、`ELSE NULL`は省略可能  
`COUNT()`は`NULL`を数えないので同じ意味になる
